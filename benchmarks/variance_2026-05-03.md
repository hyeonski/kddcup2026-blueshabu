## 추정 원인: OpenRouter provider routing

`qwen/qwen3.5-35b-a3b`는 OpenRouter에서 여러 백엔드 제공자가 서빙하며 라우팅된다. 같은 model ID여도:

- 양자화 (FP16 vs Q4 vs Q8) 가 다를 수 있음
- 추론 엔진 (vLLM vs SGLang vs Ollama) 가 다를 수 있음
- Sampling 구현 디테일이 미세하게 다를 수 있음 (특히 temp=0의 tie-breaking)

이 모든 차이가 ReAct 루프에서 누적되면 **다른 trajectory**로 발산할 수 있다. 특히 추론 step 8~9개를 거치는 multi-hop 분석에서는 한 step의 작은 차이가 다음 step 전체를 바꿈.

## 함의

1. **Master HEAD 점수의 실측 범위는 약 0.42 ~ 0.52**, 단일 런으로 보면 불확실성이 크다.
2. **개선 효과 < 0.10이면 noise에 묻힐 가능성** — `9e76fc3` (0.58 → 0.62, +0.04) 같은 작은 효과는 단발 실행으로 검증 불가능.
3. **앞으로의 측정은 다음 중 하나가 필요:**
   - 동일 변경에 대해 N=3 이상 재실행 후 평균 (시간/비용 N배)
   - OpenRouter `provider.order` 또는 `provider.only` 옵션으로 단일 백엔드 고정
   - DashScope 직접 호출처럼 provider가 단일 출처인 경로로 전환
4. **공식 채점은 단일 백엔드** (Qwen 자체 호스팅)일 가능성이 높으므로, OpenRouter provider routing 분산은 우리 dev 환경의 **인공물**이다. 그래도 우리가 변경의 효과를 측정하려면 dev 분산을 줄여야 한다.
